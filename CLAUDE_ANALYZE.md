## Итог

- Время выполнения снизилось в **1.5–5 раз**, объём аллокаций — в **2–20 раз** в зависимости от сценария. Парсинг выражений стал в 3 раза быстрее.
- Самый большой оставшийся резерв — `validateInput`: полный обход входного документа при каждом `evaluate()`. Он занимает от 60 до 90% времени на запросах «большой документ, маленький запрос». Поведение по умолчанию не менял, только ускорил сам обход.
- Найдены и исправлены несколько серьёзных багов:
  - гонка данных: при конкурентных вызовах одного выражения `$$` возвращал чужой входной документ в 83% вызовов;
  - `$sort` с функцией-компаратором падал на массивах с повторами;
  - зависшие `$now()`/`$millis()` на рабочих потоках;
  - утечки памяти через `ThreadLocal` и окружение выражения.
- Проверка:
  - все 1766 тестов зелёные (1756 исходных и 10 новых);
  - дифференциальный прогон 63 выражений на старой и новой сборке даёт побайтно одинаковый вывод.

## Методика

- **Окружение:** JDK 25 (Temurin), Windows 10, slf4j без провайдера (NOP-логгер, т.е. логирование почти бесплатно; с logback разница была бы больше).
- **Данные:** синтетический документ в формате `dataset5` (Account → Order → Product): 200 заказов по 25 товаров, всего 5000 товаров и около 60 тыс. JSON-узлов.
- **Харнесс:** собственный, без JMH. Прогрев около 1.8 с, затем замер 3 с на сценарий. Время на операцию берётся из `System.nanoTime`. Аллокации на операцию — из `com.sun.management.ThreadMXBean.getThreadAllocatedBytes`. Шум между прогонами ±10–15%.
- **Профилирование:** JFR (`-XX:StartFlightRecording settings=profile`), анализ через `jfr view hot-methods / allocation-by-class / allocation-by-site`.
- **Baseline:** классы, собранные из `HEAD` (`git archive`) с `--release 11`.

## Главная находка: validateInput

[Functions.java](src/main/java/com/dashjoin/jsonata/Functions.java), `validateInput()`. Метод вызывается из `Jsonata.evaluate(input, bindings)` при `validateInput == true` (это значение по умолчанию). Он рекурсивно обходит **весь** входной документ на **каждом** вызове.

Стоимость не зависит от запроса. Даже если выражение трогает 1% документа, проверяется 100%. В замерах это:
- **path:** 62% времени в baseline и 69% после оптимизаций;
- **transform по `Order[0]`:** 91% времени.

Что сделано: порядок проверок изменён так, чтобы `String`/`Number`/`Boolean` шли первыми. Ключи-строки больше не вызывают рекурсию, а `RandomAccess`-списки обходятся по индексу. Это ускоряет сам обход, но порядок сложности остаётся O(размер документа).

Рекомендации:
1. Для данных, полученных из Jackson/Gson или собственного `Json.parseJson`, вызывать `setValidateInput(false)`: такие данные валидны по построению.
2. В перспективе заменить полный обход ленивой проверкой типа при обращении к значению (`Functions.lookup`, `Signature.getSymbol`, `Functions.string`). Тогда стоимость будет пропорциональна тому, что реально читает запрос.
3. Либо поменять значение по умолчанию на `false` с явным предупреждением в документации.

## Внесённые оптимизации

### 1. Вызов встроенных функций

[Signature.java](src/main/java/com/dashjoin/jsonata/utils/Signature.java), [Functions.java](src/main/java/com/dashjoin/jsonata/Functions.java), [Jsonata.java](src/main/java/com/dashjoin/jsonata/Jsonata.java) (`JFunction`).

**Компиляция regex на каждом вызове.** Если аргумент подставлялся из контекста (`SKU.$substring(0,3)`, `Price.$round()`, `$string()` без аргументов), `Signature.validate()` выполнял `Pattern.matches(param.regex, contextType)`, т.е. компилировал regex при каждом вызове функции.
- **Что изменено:** при разборе сигнатуры для каждого параметра с `-` один раз вычисляется таблица `boolean[] contextAccepts` по всем 8 символам типов (`asnblfom`). Проверка стала обращением к массиву.
- **Эффект:** fnContext ×3.9, аллокации 15.2 МБ → 1.7 МБ на прогон.

**Сопоставление строки типов аргументов с regex сигнатуры.** На каждом вызове строилась строка типов через `suppliedSig += getSymbol(arg)`, создавались `Matcher`, `match.split("")` (массив однобуквенных строк) и неиспользуемый `new ArrayList<>()`.
- **Что изменено:**
  - строка типов собирается в `char[]`;
  - результат сопоставления (группы regex) кэшируется в `ConcurrentHashMap<String, String[]>` по строке типов. Алфавит типов маленький, у одной функции встречаются единицы разных строк вроде `"s"`, `"sn"`, `"snn"`. Размер кэша ограничен 256;
  - `split("")` заменён обходом по символам;
  - `getSymbol` возвращает `char` (`getSymbolChar`), сравнения стали символьными.

**Повторный разбор сигнатур.** Каждый `new Signature(...)` заново разбирал строку и компилировал regex. В частности, `evaluateTransformExpression` создаёт `new JFunction(transformer, "<(oa):o>")` на каждом вычислении `|...|`.
- **Что изменено:** глобальный кэш разобранных сигнатур (`PARSED`, ограничен 1024). Новый экземпляр берёт из кэша неизменяемые `_params`/`_regex`, своим остаётся только `functionName`.

**`Functions.call`.**
- Было: `m.getParameterTypes()` (клонирует массив) вызывался трижды на вызов, включая `JFunction.getNumberOfArgs`. Затем шла цепочка `new ArrayList<>(args)` → дополнение `null` → `toArray()`.
- Стало: `Class<?>[] parameterTypes` кэшируется в `JFunction` при создании, а массив аргументов для `Method.invoke` собирается сразу.

**`substr` / `leftPad` / `rightPad`.** Выполняли `String.intern()` для каждой входной строки. Это медленный поиск в глобальной таблице строк JVM, к тому же засоряющий её строками из пользовательских данных, а результат использовался только для подсчёта code points.
- **Что изменено:** `intern()` убран. Паддинг собирается через `String.repeat` вместо `padding += padStr` в цикле.

### 2. Квадратичные алгоритмы → линейные

[Jsonata.java](src/main/java/com/dashjoin/jsonata/Jsonata.java), [Utils.java](src/main/java/com/dashjoin/jsonata/Utils.java), [Functions.java](src/main/java/com/dashjoin/jsonata/Functions.java).

**`Functions.append` в циклах.** `append(a, b)` всегда создаёт копию `a`. Там, где он вызывается в цикле с накоплением, получается O(n²). Таких мест четыре:
- `evaluateGroupExpression` — накопление элементов группы: `groups.get(key).data = append(groups.get(key).data, item)`. При 600 элементах на ключ это примерно 180 тыс. копирований ссылок на каждый ключ;
- `evaluateUnary`, конструктор массива `[...]`: `result = append(result, value)`;
- `evaluateWildcard`: `results = append(results, flatten(value))`;
- `reduceTupleStream`: `result.put(prop, append(result.get(prop), ...))`.

Что изменено: новый класс `Utils.Appender`. Первое добавление выполняется через `Functions.append`, поэтому полностью сохраняется прежняя семантика: флаги `JList`, сокращённый возврат `RangeList`, правила для `null`. После этого аккумулятор хранит собственный, никому больше не доступный список и добавляет в него на месте. Заодно в `evaluateGroupExpression` убрано тройное `groups.get(key)` и лишний `new GroupEntry()` на каждый элемент.

`Functions.append` тоже стал дешевле: результат создаётся сразу нужной ёмкости, а не через `createSequence(arg1)` с последующим `new JList<>(arg1)`, т.е. двойным копированием.

Эффект: groupBy ×5.1, аллокации 24 МБ → 1.4 МБ на прогон.

**order-by `^(...)`** (`evaluateSortExpression`). Компаратор на каждом сравнении вычислял выражение ключа для обоих элементов, т.е. 2·n·log₂n вычислений. Для 5000 элементов это около 120 тыс. вычислений вместо 5000. В tuple-стримах к этому добавлялось копирование кортежа во фрейм дважды на сравнение.
- **Что изменено:** каждый элемент оборачивается в `SortItem` с ленивым массивом ключей. Ключ терма вычисляется при первом обращении и запоминается. Вычисляются те же термы, что и раньше (второй терм — только при равенстве первого), ошибки T2007/T2008 выбрасываются там же. Сортировка остаётся стабильной (`List.sort`), результат имеет тот же тип `ArrayList`.
- **Эффект:** sort ×5.2, аллокации 25 МБ → 1.25 МБ на прогон.

### 3. Накладные расходы на каждом узле AST

[Jsonata.java](src/main/java/com/dashjoin/jsonata/Jsonata.java), [Parser.java](src/main/java/com/dashjoin/jsonata/Parser.java).

**Поиск колбэков.** `_evaluate` на каждом узле выполнял `environment.lookup("__evaluate_entry")` и `lookup("__evaluate_exit")`. Это поиск по всей цепочке фреймов вплоть до `staticFrame` с ~65 встроенными функциями, по два хэш-поиска (`containsKey` + `get`) на каждом уровне.
- **Что изменено:** `Frame` хранит поля `entryCallback`/`exitCallback`, наследует их от родителя при создании и обновляет в `bind()`, когда привязываются эти имена. Таймбоксы и `setEvaluateEntryCallback` работают как раньше.

**`getPerThreadInstance()` на каждом узле.** Каждый вызов `evaluate(Symbol, ...)` выполнял `ThreadLocal.get()` и сохранял/восстанавливал поля экземпляра. Это заменено контекстом на один вызов `evaluate()`, см. пункт 3 в разделе [Найденные и исправленные баги](#найденные-и-исправленные-баги).

**Логирование в горячем пути.**
- Было: `log.debug("eval expr={} type={}", ...)` и `log.debug("evalName {}")` на каждом узле, `log.debug("variable name={} val={}")` на каждом чтении переменной, ещё три `log.debug` в `Parser.advance`/`expression` на каждом токене. Даже без вывода с реальным бэкендом (logback) это проверка уровня на каждом узле.
- Стало: эти вызовы удалены.

**`""+expr.value`.** По JLS конкатенация строк всегда создаёт **новый** объект `String`; в профиле это `StringConcatHelper.newStringOf`. Новая строка к тому же заново считает `hashCode` при поиске в map. Кроме того, токенайзер создаёт значения односимвольных операторов как `Character`, так что каждое вычисление `a + b` аллоцировало строку `"+"`.
- **Что изменено:**
  - в `Parser.processAST` значения бинарных и унарных узлов приводятся к `String` один раз при парсинге;
  - в evaluator везде, где было `""+value` (`evaluateBinary`, `evaluateUnary`, `evaluateBindExpression`, `applyProcedure`, `evaluateStages`), используется хелпер `str(value)` без копирования. Для конструктора массива добавлен хелпер `isValue(value, "[")`.

**`evaluateStep`.** Создавал два промежуточных `JList` на каждый шаг пути на каждом вычислении: сначала собирались результаты, затем «сплющивались» во второй список.
- **Что изменено:** результаты сплющиваются сразу в один список. Отдельно держится только первый результат: если он окажется единственным на последнем шаге и это массив, его нужно вернуть как есть.

**Сравнение `=` / `!=` / `in`.**
- Было: `lhs.getClass().getSimpleName()` вызывался только ради проверки на `null`. Обе стороны упаковывались в `Double` для `equals`. `in` оборачивал скаляр в `ArrayList`.
- Стало: `isEqual()` сравнивает `doubleToLongBits` примитивов (это в точности семантика `Double.equals`, включая NaN и -0.0) без боксинга.

**Арифметика.** `evaluateNumericExpression` передавал `double` в `convertNumber(Number)`: автобоксинг `Double`, затем ещё одна аллокация `Integer`/`Long`/`Double`. Добавлены перегрузки `Utils.convertNumber(double)` и `convertNumber(long)` с той же семантикой (NaN → null, Infinity → D1001). Перегрузка для `long` нужна, чтобы `RangeList.get` не терял точность выше 2⁵³.

**Ёмкость синглтон-последовательностей.** `createSequence(el)` создавал `JList` с ёмкостью 10 под один элемент. Таких списков много: обёртка входа в `evaluatePath`, фильтры, группировки. Теперь ёмкость 1.

**Мелочи:**
- `toBoolean` для массивов: stream с подсчётом всех элементов заменён циклом с ранним выходом;
- `$string(x, true)`: строка отступа `indent + "  "` строится один раз на контейнер, а не на каждый элемент, и только при `prettify`.

### 4. Фреймы (переменные)

[Jsonata.java](src/main/java/com/dashjoin/jsonata/Jsonata.java), класс `Frame`.

**Хранение переменных.** Каждый `Frame` держал `LinkedHashMap`, даже если в нём не было ни одной переменной. Фреймы создаются на каждый блок `( ... )` (это любые скобки), на каждый вызов лямбды и на каждый кортеж. Поиск выполнял `containsKey` + `get` на каждом уровне, причём рекурсивно.
- **Что изменено:** до 8 переменных хранятся в двух маленьких массивах `names`/`values`, которые создаются при первом `bind`; поиск линейный. При большем числе переменных фрейм переходит на `HashMap` — это нужно для `staticFrame` с ~65 функциями. Поиск по цепочке стал итеративным: один проход по фрейму с маркером `UNBOUND`.

**`createFrameFromTuple`.** Копировал весь кортеж (`LinkedHashMap`) в новый фрейм для каждого кортежа на каждом шаге tuple-стрима, на каждом элементе фильтра и в каждом сравнении сортировки.
- **Что изменено:** у фрейма появилось поле `tuple`, ссылка только для чтения на map кортежа. Поиск: сначала собственные переменные, затем кортеж, затем родитель. Копирования больше нет. Кортежи не модифицируются, пока созданные из них фреймы используются; это проверено по местам изменения (`evaluateStages`/index меняет только выходные кортежи).

### 5. `$clone` и transform

[Functions.java](src/main/java/com/dashjoin/jsonata/Functions.java), `functionClone` и новый `cloneJson`.

Раньше клонирование работало через JSON-текст: `Json.parseJson(string(arg, false))`, т.е. сериализация всей структуры в текст и обратный парсинг. Это происходит при каждом применении `|...|`.

Теперь используется прямое глубокое копирование, которое воспроизводит результат JSON-круга в точности:
- `Double` округляется до 15 значащих цифр, как в `string()`;
- целые `Double` становятся `Integer`/`Long`;
- `Long` идёт через `double`, как это делал парсер;
- `NULL_VALUE` → `null`;
- функции внутри структуры → `""`;
- `Map` → `LinkedHashMap`, `List` → `ArrayList`.

Эквивалентность проверяется тестом `testCloneSameAsJsonRoundTrip`, который сравнивает результат с самим JSON-кругом.

### 6. Парсинг

[Tokenizer.java](src/main/java/com/dashjoin/jsonata/Tokenizer.java), [Parser.java](src/main/java/com/dashjoin/jsonata/Parser.java), [Jsonata.java](src/main/java/com/dashjoin/jsonata/Jsonata.java).

**Токенайзер.** Регулярное выражение для чисел (`Pattern.compile`) компилировалось на каждом токене. Вдобавок `path.substring(position)` копировал **весь остаток выражения** на каждом токене, что даёт O(n²) от длины выражения.
- **Что изменено:** статический `Pattern` и `matcher(path).region(position, length).lookingAt()`.
- **Эффект:** парсинг ×3, аллокации 91 → 32 КБ на выражение.

**Состояние парсера.** Парсер переиспользуется в пределах потока, но список `ancestry` (оператор `%`) и `errors` никогда не очищались. `ancestry` рос с каждым разобранным выражением, это утечка памяти на поток. Теперь оба списка и `ancestorIndex` сбрасываются в начале `parse()`. `ancestorLabel` намеренно не сбрасывается, чтобы метки оставались уникальными между выражениями (это важно для `$eval`).

**Блокировка в `getParser()`.** Метод был `static synchronized`, т.е. глобальная блокировка при каждом создании выражения. Теперь это `ThreadLocal.withInitial(Parser::new)` без синхронизации: `ThreadLocal` и так разный для каждого потока.

## Найденные и исправленные баги

Баги 1–3 воспроизведены на baseline отдельной программой (`Repro.java` в scratchpad).

| # | Проблема | Старая сборка | Новая сборка |
|---|---|---|---|
| 1 | `$$` при конкурентных вызовах одного выражения (8 потоков × 20 000 вызовов) | **132 238 из 160 000** неверных результатов | 0 |
| 2 | `$millis()` на потоке, отличном от создавшего выражение | не меняется: `1790971687830 → 1790971687830` | растёт |
| 3 | `$x := ($exists($x) ? $x : 0) + 1`, три вызова подряд | `1, 2, 3` | `1, 1, 1` |
| 4 | `$sort($, function($a,$b){ $a > $b })` на 300 элементах с повторами | падение в **200 из 200** прогонов | работает |
| 5 | Лямбда с сигнатурой внутри `?:` | `NotSerializableException` при парсинге | парсится |

**1. Гонка `$$` (корневой вход).** В `Jsonata.evaluate(input, bindings)` при `bindings == null` выполнялось `exec_env = environment`, т.е. `$` записывался в **общее** окружение скомпилированного выражения. Если два потока вычисляли одно выражение, `$$` в одном из них видел вход другого. Вдобавок окружение держало ссылку на последний входной документ после завершения вычисления.

Исправление: каждый вызов теперь работает в собственном дочернем фрейме. Кроме того, появилось поле `globalEnvironment` — корневое окружение выражения, которое не меняется во время вычисления. В него пишут `assign`/`registerFunction`, и от него создаётся фрейм каждого вызова. Раньше корень брался из поля `environment`, которое `_evaluate` на потоке-создателе временно перезаписывал текущим фреймом.

**2. `$now()` / `$millis()` на рабочих потоках.** Время бралось из `Jsonata.current.get().timestamp`, т.е. из копии экземпляра для данного потока. Эта копия создавалась один раз, а `timestamp` обновлялся только у исходного экземпляра. На любом потоке, кроме создавшего выражение, время «замерзало».

**3. `ThreadLocal current` и сама схема «экземпляр на поток»:**
- конструктор `Jsonata` вызывал `current.set(this)`, а значит любой `jsonata(expr)`, включая `$eval` внутри вычисления, переключал контекст потока. Отсюда хрупкость вокруг `$eval` (issues #90/#93);
- `getPerThreadInstance()` возвращал «последний экземпляр, использованный в потоке», а не экземпляр данного выражения;
- в пуле потоков каждый поток навсегда удерживал последний `Jsonata` вместе с окружением и входом.

Исправление: публичный `evaluate()` создаёт лёгкий объект-контекст `new Jsonata(this)` на один вызов. В нём хранятся текущий вход, окружение и `timestamp`. Контекст выставляется в `ThreadLocal` один раз на вызов, а в `finally` восстанавливается внешний контекст или вызывается `ThreadLocal.remove()`. Конструктор больше не трогает `ThreadLocal`. Внутренний `evaluate(Symbol, ...)` работает с `this` без обращения к `ThreadLocal`, что одновременно убирает накладные расходы на каждом узле.

**4. `$sort` с функцией-компаратором.**
- `Functions.sort` передавал в `List.sort` «компаратор», который возвращал `1`, если функция вернула true, и `-1` во всех остальных случаях, включая равные элементы. Это нарушает контракт `Comparator`: `compare(a,b)` и `compare(b,a)` оба равны −1. TimSort это обнаруживает и бросает `IllegalArgumentException: Comparison method violates its general contract!`.
- Даже когда исключения не было, порядок равных элементов отличался от спецификации. В `test/test-overrides.json` для `function-sort/case009` и `case010` были записаны «альтернативные» результаты с пояснением «jsonata expects the native order to be preserved».
- Исправление: стабильная сортировка слиянием с той же семантикой, что в jsonata-js. Деление `floor(n/2)`; при слиянии правый элемент берётся первым, если `comparator(left, right)` вернул true. Оба override удалены, тесты сверяются с эталоном jsonata.

**5. Лямбда с сигнатурой внутри `?:` / `??`.** `Parser.clone()` использует Java-сериализацию, а `Signature.Param` не был `Serializable`, поэтому парсинг падал с `NotSerializableException`. Теперь `Param` сериализуем. Кэш совпадений в `Signature` помечен `transient` и восстанавливается в `readObject`.

**6. Мутация входа вызывающего.** `evaluateGroupExpression` при пустом входе делал `input.add(null)`, т.е. мог изменить список, принадлежащий пользователю (например, `[]` из входных данных). Теперь используется `Collections.singletonList(null)`.

**7. Нестатические методы в пользовательских функциях.** `Functions.call` вызывал `m.invoke(null, ...)` вместо `m.invoke(instance, ...)`. Нестатические методы, зарегистрированные через `Jsonata.function(name, sig, clazz, instance, method)`, падали с NPE.

## Что ещё стоит сделать (не внедрено)

Отсортировано по ожидаемой пользе.

1. **`validateInput`.** Подробности и варианты — в разделе [Главная находка: validateInput](#главная-находка-validateinput). Это наибольший резерв для типичных сценариев.

2. **`Utils.convertNulls` на выходе.** Это ещё один полный обход результата при каждом вызове, причём изменяющий данные **на месте**. Если результат содержит части входа, возвращённые по ссылке (например, `Account`), обход идёт по входу и может его менять. Варианты:
   - вести в контексте флаг «`NULL_VALUE` мог попасть в результат»: литерал `null`, `lookup` ключа со значением null, `NULL_VALUE` во входе или в `bindings`;
   - делать копирование при записи (copy-on-write).

3. **`Parser.clone` через Java-сериализацию** (используется для `?:` и `??`). Разбор `a.b.c ?: d` занимает **245 мкс**, а эквивалентного `a.b.c ? a.b.c : d` — **6 мкс** (×40). Ещё хуже с памятью. `Parser.Symbol` — нестатический внутренний класс, поэтому сериализуется и поле `this$0`, т.е. весь `Parser`: `symbolTable` примерно с 50 шаблонами, `lexer`, `node` и т.д. В итоге клонированное поддерево ссылается на **десериализованную копию всего парсера**, и эта копия живёт столько же, сколько скомпилированное выражение. Решения:
   - явное глубокое копирование AST с `IdentityHashMap`, чтобы сохранить общие ссылки (slot, ancestor);
   - или сделать `Symbol` статическим вложенным классом.

4. **`evaluateTupleStep`.** Для каждого выходного кортежа выполняется `new LinkedHashMap()` + `putAll(всех привязок входного кортежа)`. Сложность O(шагов × кортежей × привязок). Нужен связанный (persistent) кортеж: ссылка на родительский кортеж плюс собственные 1–2 привязки.

5. **`partialApplyNativeFunction`.** При каждом вычислении `$substring(?, 0, 3)` заново генерируется и **парсится** строка `function($a, $b, $c){ $substring($a, $b, $c) }`. AST стоит кэшировать по (функция, арность).

6. **Встроенные функции через рефлексию.** `Method.invoke` требует массив аргументов, боксинг и обёртку исключений. Лучше явные лямбды, см. пункт 4 в разделе [Типизация и архитектура](#типизация-и-архитектура).

7. **`Functions.string(Double)`.** На каждое дробное число создаётся `new BigDecimal(d, MathContext(15))` + `stripTrailingZeros().toString()` + `replace`. Нужен быстрый путь: если у `Double.toString(d)` не больше 15 значащих цифр, использовать его.

8. **`switch` по строке `expr.type` на каждом узле.** Кроме того, в некоторых местах строки сравниваются через `==` (`expr.procedure.type == "path"`), что работает только потому, что литералы интернированы. Лучше `enum` или полиморфные узлы.

9. **`isParallelCall`.** Флаг пишется в общие фреймы (`environment.isParallelCall = idx > 0`), что является гонкой при многопоточности. Кроме того, `Timebox` считает глубину по этому флагу, и он может отличаться на входе и выходе из узла.

10. **Строковые литералы в токенайзере.** Собираются через `qstr += currentChar`, это O(n²) для длинных литералов. Нужен `StringBuilder`.

11. **Сортировка с функцией-компаратором.** Каждый вызов компаратора — это полноценный вызов лямбды: фрейм и т.д. Это ожидаемо, но для сортировки по ключу стоит рекомендовать `^(...)` вместо `$sort(..., function...)`.

## Типизация и архитектура

### Данные стоит оставить «сырыми», а типизировать движок

Главное преимущество Java-порта в том, что он работает прямо поверх `Map`/`List`/`String`/`Number`/`Boolean` из Jackson, Gson или собственного парсера, без копирования. Перевод входа в типизированное дерево (`sealed interface JValue permits JString, JNumber, ...`) стоил бы O(размер документа) на каждом вызове. Это ровно та проблема, которую мы видим с `validateInput`, где обход забирает 60–90% времени. Поэтому типизацию стоит направить на внутренние структуры движка.

### 1. AST

**Сейчас:**
- один класс `Parser.Symbol` примерно с 55 полями (`lhs`, `rhs`, `steps`, `predicate`, `stages`, `procedure`, `arguments`, `body`, `condition`, `then`, `_else`, `pattern`, `update`, `delete`, `group`, `lhsObject`, `terms`, `slot`, `ancestor`, …), из которых каждому типу узла нужны 3–6;
- каждый узел занимает примерно 240 байт;
- `type` — строка, диспетчеризация — `switch` по строке;
- `value` — `Object` (то `String`, то `Character`, то `Number`, то `Pattern`).

**Предлагается:**
- иерархия узлов: `sealed interface Node` и final-классы `PathNode`, `NameNode`, `BinaryNode(BinaryOp op)`, `LiteralNode`, `FunctionCallNode`, `LambdaNode`, `BlockNode`, `ConditionNode`, `TransformNode` и т.д. Операторы — `enum BinaryOp { ADD, SUB, EQ, AND, ... }`;
- «компиляция» AST в исполняемое дерево: `Object Node.evaluate(EvalContext ctx, Object input, Frame env)` с виртуальной диспетчеризацией вместо `switch` по строке;
- узлы кэшируют подготовленные данные: значения литералов, флаги путей (`consarray`, `keepSingletonArray`), при возможности — разрешённые встроенные функции (если имя не переопределено);
- ожидаемый эффект на «узловых» сценариях (objCons, parentOp, path): ещё ×1.5–3.

### 2. Типы времени выполнения вместо флагов и соглашений

| Сейчас | Предлагается |
|---|---|
| Лямбда — это тот же `Symbol` (`_jsonata_lambda = true`), ~240 байт на каждое создание замыкания | Класс `Closure { params, body, env, input, signature }`, ~40 байт |
| Функции: `JFunction`, `Symbol`-лямбда, `Fn0`..`Fn8`, `JFunctionCallable`, `Pattern` (regex); проверки разбросаны: `applyInner` (4 ветки `instanceof`), `Signature.getSymbol`, `Functions.type`, `isFunctionLike` | Единый интерфейс `JsonataFunction { Object apply(EvalContext, List<Object> args); Signature signature(); int arity(); }` с адаптерами |
| Последовательность — `JList extends ArrayList` с пятью boolean-флагами (`sequence`, `outerWrapper`, `tupleStream`, `keepSingleton`, `cons`), которые меняются по ходу вычисления | Отдельные типы `Sequence`, `TupleStream`, `ConsArray`; правило «один элемент → значение» — в одном месте |
| Кортеж — `Map` с ключом `"@"` | Класс `Tuple { Object context; Tuple parent; bindings }` (заодно решает пункт 4 из раздела [Что ещё стоит сделать](#что-ещё-стоит-сделать-не-внедрено)) |
| `undefined` = Java `null`, JSON null = `NULL_VALUE` | Явные константы `Undefined.INSTANCE` / `JsonNull.INSTANCE` внутри движка, конвертация на границе API |

### 3. Тип значения — в одном месте

Цепочки `instanceof` дублируются в `Signature.getSymbol`, `Functions.type`, `Functions.string`, `Functions.toBoolean`, `Functions.validateInput`, `Jsonata.isFunctionLike`. Предлагается `enum JType { UNDEFINED, NULL, BOOLEAN, NUMBER, STRING, ARRAY, OBJECT, FUNCTION }` с методом `JType.of(Object)` и `switch` по нему.

### 4. Встроенные функции

**Сейчас:**
- `defineFunction("substring", "<s-nn?:s>")` ищет метод по имени через рефлексию (`getFunction` берёт **первый** публичный метод с таким именем, что хрупко при перегрузках);
- аргументы приводятся по Java-типам параметров; есть особые случаи: «первый параметр List — обернуть», «единственный параметр JList — передать все аргументы»;
- вызов идёт через `Method.invoke`.

**Предлагается:** явная типизированная регистрация вида

```java
define("substring", "<s-nn?:s>", (ctx, a) -> substring(a.str(0), a.num(1), a.num(2)));
```

Это быстрее (нет `Method.invoke`, массива и обёртки исключений), безопасно при рефакторинге (переименование метода не ломается молча) и проверяется компилятором.

### 5. Контекст вычисления и публичный API

- Сейчас `Jsonata` совмещает три роли: скомпилированное выражение (неизменяемое), состояние вычисления (`input`, `environment`, `timestamp`) и через статический `staticFrame` глобальный реестр функций. Частично это уже разделено (контекст на один вызов), но полное разделение — `CompiledExpression` + `EvalContext`, передаваемый явно, — уберёт `ThreadLocal` совсем.
- В публичный API можно добавить `<T> T evaluate(Object input, Class<T> type)` или обёртку результата.
- Опционально: адаптер `JsonAdapter<N>`, чтобы вычислять прямо поверх `JsonNode` Jackson без конвертации.

### 6. Сборка

Проект собирается под Java 11. В родительском [pom/pom.xml](pom/pom.xml) задан `maven.compiler.target = 20`, но `maven-compiler-plugin` подставляет `${maven.compiler.source}` и в `source`, и в `target`. `sealed`, records и pattern matching для `switch`, удобные для пунктов 1–3, требуют Java 17+. Если переход возможен, это стоит сделать до рефакторинга AST.

## Проверка корректности

1. **`mvn test`:** 1766 тестов, 0 падений, 3 пропущены (как и до изменений). Из них 1756 исходных и 10 новых в [OptimizationTest.java](src/test/java/com/dashjoin/jsonata/OptimizationTest.java). Новые тесты покрывают:
   - эквивалентность `$clone` JSON-кругу (числа, null, `NULL_VALUE`, функции, вложенность, экранирование);

   - конструктор массива с вложенными массивами и диапазонами;
   - однократное вычисление ключа сортировки и стабильность сортировки по нескольким термам;
   - `$sort` с функцией на 300 элементах с повторами (стабильность);
   - `$$` при 8 параллельных потоках;
   - `$millis()` на рабочем потоке;
   - отсутствие удержания контекста в `ThreadLocal`;
